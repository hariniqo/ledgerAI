# LedgerTrue — Debug Audit

Scope note: this is a real audit against the actual codebase (Google AI Studio applet: React 19 + Vite 6 + Express server bundle, Firebase Auth/Firestore, `@google/genai`). It does not use `FastAPI`, `LangGraph`, or any TerraMind-X code, per the brief. Items are only listed where something was actually found in the code — nothing here is guessed or padded to fill a template.

| # | Issue | File | Line/Component | Severity | Root Cause | Impact | Fix | Status |
|---|---|---|---|---|---|---|---|---|
| 1 | Production server bundle crashes on boot | `server.ts` | 9–10 (pre-fix) | **CRITICAL** | `__filename`/`__dirname` were derived from `import.meta.url`, but `npm run build` bundles `server.ts` to CommonJS via `esbuild --format=cjs`. `import.meta` is empty under CJS, so `fileURLToPath(import.meta.url)` throws a `TypeError` unconditionally at module load — esbuild even emits a build-time warning for this. The value was computed but never actually used elsewhere in the file. | `npm run build && npm start` (the documented production path) never serves a single request — the process dies on the first line after `dotenv.config()`. | Removed the unused, ESM-only `__filename`/`__dirname` computation and documented why (CJS-safe `require.main.filename` pattern noted in a comment for if it's ever needed). | **FIXED** — verified: build no longer warns, `node dist/server.cjs` boots and answers `GET /api/health`. |
| 2 | Unsafe floating-point equality on money in the reconciliation core | `src/engine/reconciler.ts` | `reconcileStreams()`, exact-match branch | **CRITICAL** | Exact-match check was `amountDiff === 0`. JS floats aren't exact for decimal money (`0.1 + 0.2 !== 0.3`); any internal amount arrived at via floating-point summation could differ from the "same" gateway amount by ~1e-16 and fail strict equality. | Because the discrepancy branch only fired for `amountDiff > 0.01`, a value in `(0, 0.01]` matched **neither** branch — the transaction was silently dropped: not matched, not flagged, not counted anywhere. This is exactly the class of bug Phase 3 asked to guard against. | Introduced `MONEY_EPSILON = 0.005` (half a cent) and made the two branches partition on it exactly (`< MONEY_EPSILON` vs `>= MONEY_EPSILON`), closing the gap. | **FIXED** — regression test added (`tests/reconciler.test.ts`, `0.1 + 0.2` case) and passing. |
| 3 | Hallucinated/non-existent Gemini model name used for two live API calls | `server.ts` | `/api/gemini/generate-scenario` (was line 203), `/api/msme/explain` (was lines 271/284) | **HIGH** | `"gemini-3.8-flash"` is not a real model id — every other call site in the same file correctly uses `"gemini-2.5-flash"`. | Any request to these two endpoints with a valid `GEMINI_API_KEY` configured would fail the live API call (falls back to the heuristic response only via the `catch` block, silently masking the failure and always serving degraded output even when Gemini is available). The `source` field also mislabeled which model actually produced a response — the app's own Phase 9 rule says never to misrepresent what generated an AI insight. | Changed both the `model:` parameter and the `source:` field to `"gemini-2.5-flash"`, matching the third (working) call site. | **FIXED**. |
| 4 | Custom hash function documented and named as `simpleSha256` / "SHA-256" / "cryptographic hash" | `src/engine/crypto.ts` | `simpleSha256()`, JSDoc | **MEDIUM** | The function is actually a fast seeded multiply-xor mix (MurmurHash-style), not SHA-256, and is not cryptographically secure. It's used to build the "Merkle root" / "block hash" ledger-integrity demo view. | Misleading name/docs could cause a future engineer (or an auditor) to treat the "Merkle root" / "chain integrity" verification shown in `LedgerExplorerView` as a real cryptographic tamper-evidence guarantee, when it is a deterministic display fingerprint. This is the same "don't present a fabricated guarantee as verified fact" principle the brief applies to AI output. | Renamed to `deterministicFingerprint`, rewrote the JSDoc to state plainly it is not SHA-256/not cryptographically secure and why (needs to run synchronously, `crypto.subtle.digest` is async), and pointed to the real Web Crypto API for anyone who needs actual cryptographic integrity later. | **FIXED** (naming/docs only — behavior intentionally unchanged; it's still fine for its actual job, a demo integrity visualization). |
| 5 | No test runner configured despite `npm test`-shaped expectations | `package.json` | `scripts` | LOW | Project had `dev`/`build`/`lint`/`preview`/`clean` scripts but no `test` script and no test framework installed. | Phases 21/22/23 of the debug brief (unit/integration/e2e tests) had nothing to run against. | Added `tests/reconciler.test.ts` using Node's built-in test runner (`node:test`, zero new dependencies) covering the core reconciliation scenarios (exact match, floating-point equality, amount mismatch, fee-tolerance match, duplicate webhook, missing-in-bank, missing-in-ledger/orphaned auth, ledger invariant balance), and a `"test": "tsx --test tests/**/*.test.ts"` script. | **FIXED** (initial coverage only — see "Not done" below). |
| 6 | "Razorpay integration" is UI branding only, not a payment flow | `src/components/RazorpayAuthButton.tsx`, `RazorpayAuthModal.tsx` | n/a | INFO (not a bug) | There is no Razorpay Checkout SDK, order creation, payment callback, or secret key anywhere in the codebase — confirmed by grep across `src/`. "Razorpay" is used only as a visual/brand theme for the sign-in button ("Bank Login" styled with Razorpay's blue). Auth itself is Firebase Email/Google. | None — flagging this so the Phase 11 payment-flow checklist (order creation, success/failure callback, server-side verification, no real payments in tests) isn't mistakenly treated as "failed" or "missing" when it was never implemented as a payment flow to begin with. | No code change; documented so the health report below is accurate. | **N/A — verified as designed.** |
| 7 | Firebase Web API key hardcoded in `src/lib/firebase.ts` | `src/lib/firebase.ts` | 25–34 | INFO (not a bug) | Firebase *web* config (`apiKey`, `projectId`, etc.) is not a secret by design — Google's own docs confirm it's safe to ship client-side; access control is enforced by Firestore Security Rules, not by hiding this config. | None, provided `firestore.rules` stays correct. | Checked `firestore.rules`: reads/writes are gated on `request.auth.uid == userId` for the user's own subtree, deletes are disabled entirely.
